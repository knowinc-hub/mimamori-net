# みまもりネット 本運用化プロジェクト — Claude Code 作業指示書

## 0. この文書の使い方

このファイルをリポジトリ直下（例: `docs/PRODUCTION_PLAN.md`）に置き、Claude Code に「この指示書に従って Phase 1 から着手して」と依頼する。
各 Phase の完了時に必ず動作確認・レビューを挟むこと。**一気に全部作らない。**

---

## 1. プロジェクト概要

- **名称**: みまもりネット
- **目的**: 障害のある方などが行方不明になった際、SNSへの無制限拡散ではなく、**対象エリア内の登録メンバーだけ**に必要な情報を必要なときだけ届けるセミクローズドな見守りアプリ。
- **背景**: SNS拡散には「発見後も古い情報が残り続ける」「本人・家族が望まない形で障害特性・外見情報が広まる」「デマ混入で捜索の妨げになる（警察の注意喚起事例あり）」というリスクがある。位置情報ベースの登録制システムの方が発見率・速度ともに高いというデータもある。
- **現状**: GitHub Pages にプロトタイプを公開中
  - リポジトリ: `knowinc-hub/mimamori-net`
  - URL: https://knowinc-hub.github.io/mimamori-net/
  - 単一HTML の静的モック（バックエンドなし、データはダミー）
- **対象エリア**: 練馬区・西東京市・武蔵野市（特別支援学校の学区に対応）

## 2. 絶対に守る設計原則（変更禁止）

これはプロダクトのアイデンティティであり、機能追加の際も必ず維持する。

1. **SNS共有機能は実装しない**。シェアボタン・OGP最適化・「コピーして拡散」導線は一切作らない。むしろ転載しにくい設計にする（後述）。
2. **解決したら消える**。捜索依頼が「発見・解決」になったら、写真・氏名・特徴・連絡先は自動削除。履歴には「日時・エリア・解決した事実」のみ残す。
3. **エリア内の登録メンバーのみ閲覧可能**。未ログインで依頼詳細が見えてはいけない。
4. **登録は承認制**。誰でも即参加できるオープン登録にはしない。
5. **警察への届出が前提**。捜索依頼の投稿には警察受理番号（または届出済みであることの確認チェック）を必須とし、アプリは警察捜索の「補完」であることをUI上でも明示する。

## 3. 技術スタック（推奨構成）

| レイヤ | 技術 | 理由 |
|---|---|---|
| フロントエンド | Vite + React + TypeScript、PWA（vite-plugin-pwa） | モバイル前提。PWA化でホーム画面追加＋Web Push対応 |
| UI | Tailwind CSS | 保守しやすく、デザイントークンを統一しやすい |
| バックエンド | Firebase（Auth / Firestore / Cloud Functions / FCM / Storage） | 承認制会員・プッシュ通知・スケジュール削除が全部揃う。小規模なら実質無料圏 |
| ホスティング | Firebase Hosting へ移行（GitHub Pages はリダイレクトを残す） | Auth・FCMとの相性、独自ドメイン化も見据えて |
| CI/CD | GitHub Actions（main へのマージで自動デプロイ） | 運用引き継ぎを容易に |

**注意点（Claude Code への指示）:**
- Firebase の Scheduled Functions は Blaze プラン（従量課金）が必要。予算アラート（例: 月1,000円）を設定する手順を README に書くこと。
- もし Firebase を避けたい判断になった場合の代替は Supabase（pg_cron + Edge Functions + Web Push は自前）。ただし比較検討に時間をかけすぎない。**デフォルトは Firebase で進める。**
- 依存パッケージは最小限に。年次で運用者が変わる可能性を踏まえ、README とアーキテクチャ図（Mermaid可）を必ず整備する。

## 4. フェーズ計画

### Phase 1: UI/UX 全面改善（バックエンドなしのまま）

現行モックの画面構成（ホーム / エリア / 履歴 / 設定 / 投稿モーダル）を活かしつつ、React + Tailwind + PWA に作り直す。データ層はモック（ローカルのダミーデータ + 状態管理）で良いが、**Phase 2 で Firestore に差し替えられるよう、データアクセスをリポジトリ層に分離**しておく。

#### UI/UX 改善要件

**全体**
- モバイルファースト（375px基準）。下部タブナビゲーション維持。タップ領域は最小44×44px。
- アクセシビリティ必須: WCAG 2.1 AA 相当。利用者に高齢の家族・支援者が多い想定。
  - フォントサイズはベース16px以上、コントラスト比4.5:1以上
  - 絵文字アイコン（👁📍など）を廃止し、SVGアイコン（lucide-react）＋テキストラベル併記に変更
  - フォーム要素すべてに label、エラーはインラインで具体的に表示
- 落ち着いた配色に刷新。緊急情報を扱うため、赤の乱用を避け、「捜索中」バッジのみ警告色を使う。
- ローディング・空状態・エラー状態の3状態をすべての画面で設計する。

**ホーム画面**
- 最上部に現在のステータスを1枚のカードで明示（「現在、捜索依頼はありません」/「捜索中の依頼が○件あります」）。
- 統計（今月発見・地域メンバー数）は控えめに下部へ。数字の誇示より安心感を優先。
- 捜索依頼カードには「最終更新時刻」「発生からの経過時間」を必ず表示（古い情報の拡散を防ぐ思想をUIで体現する）。

**投稿フロー（最重要改善ポイント）**
- 現行の1枚モーダルをやめ、**ステップ式ウィザード**に変更:
  1. 種類選択（捜索依頼 / 発見報告 / 情報提供）
  2. 警察届出の確認（捜索依頼のみ。受理番号入力 or 「届出済み」チェック必須。未届けの場合は110番を促す画面を挟む）
  3. 本人情報・状況入力（写真は捜索依頼のみ添付可）
  4. 確認画面（「エリア内メンバーのみに共有されます。解決後、写真と詳細は自動削除されます」を明示）
- 緊急時に慌てて使うことを想定し、各ステップは入力項目3つ以内。途中保存（下書き）対応。

**履歴画面**
- 「解決済みは日時・エリアのみ」という設計思想を説明する固定文言を先頭に置く。
- 個人情報が残っていないことが一目でわかるカードデザイン。

**転載抑止（できる範囲で）**
- 依頼詳細の写真は長押し保存しにくくする（`pointer-events` 制御 + 薄い透かし「みまもりネット限定共有」を写真上にオーバーレイ）。完全防止は不可能である旨をREADMEに明記し、過信しない。
- ページの OGP は汎用のアプリ紹介のみ。依頼個別ページの URL 直リンクではログイン画面を表示。

**PWA**
- ホーム画面追加の案内バナー（初回のみ・閉じられる）
- オフライン時はキャッシュ済み画面＋「オフラインです」表示

#### Phase 1 完了条件
- Lighthouse: PWA 合格、Accessibility 90+
- 実機（iOS Safari / Android Chrome）での表示・操作確認
- ダミーデータで全フロー（投稿→一覧→解決→履歴）が通ること

### Phase 2: バックエンド・認証・データ実装

- **認証**: Firebase Auth（メールリンク認証を基本。パスワード管理の負担を避ける）
- **承認制の実装**:
  - 新規登録 → 「承認待ち」状態 → 管理者が承認して初めて依頼閲覧可能
  - 招待コード方式も併用（PTA・親の会・支援者団体経由で配布する想定）
  - 管理者用の簡易画面（承認/停止、投稿の非表示化）を用意。**管理画面も非エンジニアが操作できるUIにする**
- **Firestore データ設計**（例）:
  - `users`: ニックネーム、エリア、ステータス（pending/approved/suspended）、通知設定
  - `requests`: 種類、状態（active/resolved）、エリア、発生地点、作成日時、解決日時
  - `requests/{id}/private`: 氏名・特徴・写真URL・連絡先（**解決時に物理削除する対象をサブコレクションに隔離**）
  - `history`: 解決済みの日時・エリアのみを持つ別コレクション（削除処理の取りこぼし防止）
- **セキュリティルール**: approved ユーザーのみ read 可。private サブコレクションは同エリアの approved ユーザーのみ。Storage の写真も同様のルール。**ルールのユニットテスト（@firebase/rules-unit-testing）を書くこと。**
- **自動削除**: 依頼が resolved になったら Cloud Functions で private + Storage 写真を即時削除。加えて、解決忘れ対策として作成から30日経過した active 依頼は投稿者に確認通知 → 45日で自動クローズ＋削除（日次スケジュール関数）。
- **監査ログ**: 削除実行の記録（何を消したかではなく「消した事実」のみ）を残す。

### Phase 3: 通知・位置情報

- **Web Push（FCM）**: 新規捜索依頼・解決報告をエリア内メンバーに通知。iOS はPWAとしてホーム画面追加済みの場合のみ対応可能である旨をUIで案内。
- **深夜帯（22時〜6時）通知オフ設定**を尊重する送信ロジック。
- **位置情報**: まずは「自治体＋町名レベルの登録エリア」でのマッチングから開始。GPSベースの「発生地点から2km以内」通知は、精度・プライバシー・実装コストを検討したうえで Phase 3 後半に判断（**最初からGPS常時取得はしない**。プライバシー面の説明コストが高い）。
- 地図表示: Leaflet + OpenStreetMap（無料）。発生地点はピンで表示、詳細住所は表示しない。

### Phase 4: 運用準備（コード外だが必須）

Claude Code には以下のドキュメント草案作成まで依頼する:
- 利用規約・プライバシーポリシー草案（個人情報の取得項目、削除ポリシー、警察届出前提、免責）
- 運用マニュアル（承認フロー、通報対応、虚偽投稿時の対応、年次の管理者引き継ぎ手順）
- 通報機能（投稿への「問題を報告」ボタン → 管理者に通知）は Phase 2 に含めて実装する

## 5. Claude Code への進め方指示

1. 最初に現行の `index.html` を読み、画面構成・文言・データ項目を把握してから Phase 1 に着手する。**既存の文言（設計思想の説明文など）は資産なので活かす。**
2. ブランチ運用: `main`（公開）/ `dev`（作業）。Phase ごとに PR を切る。
3. コミットは機能単位で日本語メッセージ可。
4. 各 Phase 完了時に `docs/` 配下へ「実装内容・未対応事項・次の判断が必要な点」を書いた完了レポートを残す。
5. 判断が必要な点（デザインの好み、課金の要否、エリア粒度など）は勝手に決めず、選択肢と推奨案を提示して確認を求める。
6. テスト: Phase 2 以降はセキュリティルールのテストを最優先。UIはE2E（Playwright）で投稿→解決→自動削除のクリティカルパスのみカバー。

## 6. やらないこと（スコープ外）

- ネイティブアプリ化（App Store / Google Play）
- SNS連携・外部共有機能全般
- 対象エリアの全国展開（まず3自治体で運用検証）
- AI による目撃情報の自動照合など高度な機能
